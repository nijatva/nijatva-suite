# RELEASE-POLICY.md

How a Nijatva app becomes a release, and how it reaches a phone. Nothing here is optional.

Verified state on **24 November 2026**: 11 apps have releases, 1 is signed and indexed, 10 are debug or unverified.

---

## 1. Vocabulary (use these words precisely)

| Word | Means |
|---|---|
| **Repo** | A GitHub repository exists. Proves nothing about the app |
| **Build** | CI produced an APK. It may be debug, unsigned or both |
| **Release** | A signed `assembleRelease` APK attached to a version tag |
| **Indexed** | The release appears in `index-v1.json` with a verified sha256 and signer |
| **Installable** | A phone installs it from the index URL |
| **Done** | Release + indexed + installs **and updates** on a real device |

"Released" without "indexed" is a download link, not a product. Never use "done" for anything less than the last row.

---

## 2. Versioning and tags

- Tags: `vMAJOR.MINOR.PATCH` — e.g. `v1.6.0`. Two-part `v1.5` is accepted by the generator but discouraged.
- **Forbidden tag patterns:** `latest`, `*`-`debug`, `*`-`preview`, dates, anything without a `v` prefix. Current violations: `nijatva-browser` publishes under `latest`; `nijatva-camera` uses tags like `v0.4.10-preview-match-debug`; `nijatva-gallery` uses `v0.1.3-appearance-debug`.
- `versionCode` increases by at least 1 per published APK. Never reuse a `versionCode`.
- `versionName` matches the tag without the `v`.
- Package name is locked before the first release: `in.nijatva.<app>` (fallback `com.nijatva.<app>`). Changing it later breaks the update path for every installed user.
- Pre-release builds go to a **draft** or a `-rc` tag that the index refuses to serve.

---

## 3. Build requirements (release variant)

A release build **MUST**:

1. come from `assembleRelease`, never `assembleDebug`;
2. be signed with the suite key, with `signingConfigs.release` wired to `KEYSTORE_BASE64` + `KEYSTORE_PASSWORD` + `KEY_PASSWORD` secrets — never a hardcoded password;
3. have `isMinifyEnabled = true` with a tested R8/ProGuard config (keeps the entry points the app actually needs);
4. have no `applicationIdSuffix` (that is debug-only);
5. have `android:debuggable="false"`;
6. declare `exported` explicitly on every component with an intent filter;
7. pass `no-gms-check` in the same workflow that builds it;
8. print and archive: `apksigner verify --print-certs` output, `sha256sum` of the APK, `aapt2 dump badging` (package, versionCode, minSdk, targetSdk, permissions).

A release build **MUST NOT**: embed a keystore, read a token from source, or run `--no-daemon --stacktrace` without also failing the job on a non-zero exit.

---

## 4. Signing

| Rule | Detail |
|---|---|
| One key for the suite | Same keystore for every app, so one fingerprint appears in the index |
| Where it lives | Two offline backups (e.g. an encrypted archive on two separate media). Never in git, never in Drive, never in an Actions artifact |
| In CI | `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_PASSWORD` repository secrets; the restored file is deleted in a `finally` step |
| Fingerprint | SHA-256 of the signing certificate recorded here and in the index generator |
| Rotation | A new key means a new package id or a documented migration build. There is no silent rotation on Android |
| Loss | If the key is lost, no installed app can ever be updated. This is the single most expensive mistake available in this project |

**Record the fingerprint here once verified:**

```
Keystore:        nijatva-release.keystore  (backup location: owner-only, not in repo)
Alias:           nijatva
Cert SHA-256:    <fill from apksigner verify --print-certs>
Created:         <date>
Photo Editor 1.5.0 signer DN: CN=Vasudev Dangaya, O=Nijatva Photo Editor, C=IN
```

## 5. CI gates

Every app workflow runs, in this order, and stops on the first failure:

1. `./gradlew check` (or `gradle check` where there is no wrapper)
2. `no-gms-check` — banned group scan on resolved classpaths
3. binary guard — `git ls-files` must contain no `.aar/.apk/.jar/.jks/.keystore`
4. `assembleRelease`
5. `apksigner verify --print-certs` — must show the suite fingerprint
6. `aapt2 dump badging` — assert `targetSdk >= 34`, assert the permission allow-list
7. upload APK + `sha256sum` + cert output as release assets on a tag

**Not a gate, but required:** a release note that states what changed, permissions added or removed, and minSdk.

---

## 6. Index rules

`index-v1.json` is generated by `nijatva-suite/tools/generate_index.py` from `apps.json` + the GitHub Releases API. It **MUST** refuse an entry when:

| Condition | Why |
|---|---|
| APK is unsigned, or signed with a debug key (`CN=Android Debug`) | Cannot be updated to a release later without uninstall |
| Signer fingerprint ≠ suite fingerprint | Split identity, unverifiable updates |
| `targetSdk < 34` (index policy `minTargetSdk`) | Store policy, matches current Android requirements |
| sha256 missing or mismatched | The download cannot be verified |
| Banned dex present (`extraBannedDex`) | The privacy claim is enforced at the gate too |
| Tag matches a forbidden pattern (`latest`, `*-debug`) | Not a release |
| `versionCode` ≤ the indexed one | Downgrade or duplicate |
| No source URL, no licence | Not auditable |

Additional index requirements:

- `apps.json` is **generated from `APP-REGISTRY.json`**, not hand-edited. A CI job fails when the two disagree.
- Every indexed entry carries: package, versionCode, versionName, APK URL, sha256, signer, minSdk, targetSdk, native code ABIs, size, permissions, source URL, issue tracker, licence, and a one-line summary (never empty — the current Photo Editor entry has an empty `summary` and `description`, which is a policy failure).
- The index is regenerated on every release, not on a schedule. Staleness is a bug: Photo Editor 1.6.0 is released while the index still serves 1.5.0.

---

## 7. Store client behaviour

- Downloads over HTTPS from the release URL, then verifies sha256 **before** handing the file to `PackageInstaller`.
- Verifies the signer of the downloaded APK matches the index fingerprint before offering an update.
- Never installs silently: the system confirmation dialog is part of the product, and the UI says so.
- `REQUEST_INSTALL_PACKAGES` is declared; Shizuku/root paths are optional power-user features, never the default.
- No account, no download tracking, no "popular apps" telemetry. The catalogue is a static JSON.
- Shows for each app: description, version, size, minSdk, permissions, release notes, source link, licence.

---

## 8. Rollback and yanking

| Situation | Action |
|---|---|
| Bad release, users unaffected yet | Delete the release, regenerate the index. Nothing to announce |
| Bad release, users already updated | Publish a higher `versionCode` with the fix. **Never** lower a `versionCode` in the index — Android will not downgrade |
| Security issue in a dependency | Patch, release, index, and state the CVE in the release note |
| Key compromised | Remove the fingerprint from the index, publish an advisory, ship a migration build |

---

## 9. Release checklist (paste into every release PR)

```
[ ] tag matches vMAJOR.MINOR.PATCH, no debug/preview/latest suffix
[ ] versionCode incremented
[ ] assembleRelease, minified, no applicationIdSuffix
[ ] signed with suite key, password from secret (no hardcoded value)
[ ] apksigner cert SHA-256 matches RELEASE-POLICY §4
[ ] no-gms-check passed in this workflow
[ ] git ls-files has no binary
[ ] sha256 recorded
[ ] index entry updated: versionCode, versionName, sha256, signer, permissions, summary
[ ] installed from the index URL on a physical phone
[ ] updated over the previous version without uninstall
[ ] release note written (changes, permissions delta, minSdk)
```

All twelve lines, or it is not a release.
